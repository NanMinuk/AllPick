# 올픽 (AllPick) 🛒

가족 구성원 모두(All)의 입맛에 맞는 식품을 골라주는(Pick) AI 추천 에이전트

**배포 링크**: https://minuk-kim-20260414.vercel.app/

---

## 기술 스택

| 레이어 | 기술 |
|---|---|
| 프론트엔드 | React |
| 백엔드 | Node.js |
| AI | OpenAI GPT-4o (추천/분석) + GPT-4o-mini (데이터 enrichment) + text-embedding-3-small (벡터 검색) |
| DB | MongoDB Atlas (Mongoose, 세션 기반 멀티 유저) |
| 관측성 | LangFuse (trace · span · generation 단위 모니터링) |
| 데이터 수집 | 네이버 쇼핑 검색 API + GPT 보충 |
| 호스팅 | Render (백엔드) + Vercel (프론트엔드) |

---

## 핵심 기능

- **가족 프로필 등록** — 구성원별 맵기·알러지·기피재료·선호 음식·식감 입력
- **전체 상품 탐색** — 97개 식품, 카테고리 필터 / 검색 / 페이지
- **AI 추천** — 가족 전체 및 구성원별 탭으로 맞춤 추천
- **구성원별 적합도 판단** — 상품별 적합/주의/부적합 판정 + 상세 근거

## 구현 포인트

**구매자 ≠ 소비자 문제 해결**
- 기존 커머스는 구매자 기준 한정 → 전체 소비자를 고려해 추천 단위를 바꾼 것이 핵심

**Two-stage 추천 파이프라인**
- Stage 1 — 임베딩 검색: 가족 프로필을 자연어로 변환 후 text-embedding-3-small로 임베딩, 사전 계산된 상품 벡터와 코사인 유사도 비교 → 상위 20개 후보 선별
- Stage 2 — LLM 재랭킹: GPT-4o가 후보 20개 중 가족 프로필(알러지·기피·선호·맵기)을 고려해 최종 순위 결정
- 에이전트 방식 대비 LLM-as-Judge 평가: **다양성 +36.7% / 적합도 +54.8%** (6개 가족 프로필, GPT-4o 블라인드 평가)
- 특히 알러지 복합 가족에서 에이전트(A)가 추천 0개를 반환한 실패 케이스를, Two-stage(B)는 안정적으로 처리

**AI 에이전트 구조 (1차 구현 → Two-stage로 발전)**
- 에이전트 도구 2개로 구성
  - `search_products(keyword, category)` — 가족 프로필에서 읽은 단서로 상품 탐색
  - `finalize_recommendation(product_ids, reasoning)` — 탐색 완료 후 최종 확정 및 루프 종료
- LLM이 프로필을 보고 직접 필요한 상품을 골라 탐색 → 토큰 효율 + 확장성

**데이터 파이프라인**
- 네이버 쇼핑 API는 성분·알러지 정보를 제공하지 않음
- 크롤링 시점에 GPT-4o-mini로 상품명 분석 → 주재료·알러지·예측 저장
- 런타임에 예측값을 활용해 추천 정확도 향상, 할루시네이션 감소

**추천 Calibration**
- 에이전트가 특정 카테고리나 유사 상품만 반복 추천하면 유저 흥미가 떨어짐
- 카테고리(간편식·가공식품·신선식품)별 최대 3개로 제한, 초과분은 후순위로 밀고 부족한 카테고리에서 채움
- 가장 적합한 상품은 상위에 유지하면서 전체 리스트는 다양하게 구성

**관측성 — LangFuse**
- Stage 1(임베딩 검색)과 Stage 2(LLM 재랭킹)를 별도 span으로 추적
- 각 추천 요청의 입력(가족 프로필)·출력(추천 상품 IDs)·모델·레이턴시를 trace로 기록
- 이상 응답 및 비용 추이를 대시보드에서 실시간 확인 가능

**세션 기반 멀티 유저**
- 브라우저마다 UUID를 localStorage에 발급, 모든 API 요청에 `x-session-id` 헤더로 전송
- MongoDB에 sessionId 단위로 가족 프로필 저장 → 다른 사용자와 데이터 완전 격리

**기타**
- AI 호출 전 코드 레벨에서 알러지 상품 제거 → 안전성 확보 + API 비용 절감
- 가족 프로필 → 자연어 변환 후 AI에 전달
- 구성원별 추천 결과 클라이언트 캐싱 → 탭 전환 시 API 재호출 없음

## 어려웠던 점

**1. 추천 대상 상품 선정 — 에이전트 도입 이유**
- 문제: 전체 상품을 프롬프트에 전부 나열하면 비용이 크고, 검색어를 코드로 고정하면 가족 구성마다 대응 불가 
- 해결: 탐색 전략 자체를 LLM에 위임 → LLM이 프로필을 읽고 어떤 키워드/카테고리를 탐색할지 스스로 판단

**2. 성분 정보 부재**
- 문제: 네이버 쇼핑 API가 성분 미제공 → 상품명만으로 적합도 예측 시 할루시네이션 빈발
- 해결: 크롤링 시 GPT가 상품명을 보고 재료·알러지·맵기 예측 저장

**3. LLM 응답 품질**
- 문제: 프로필 문구 그대로 출력("한식 스타일 선호"), 카테고리명("간편식", "치킨"...)만 반환 하는 등 품질 저하
- 해결: 판단 우선순위 명시(알러지 → 기피재료 → 맵기 → 취향) + few-shot 예시 + Chain-of-Thought 프롬프트 설계

## 아쉬운 점

- **협업 필터링 불가** — 구성원 나이대별로 실제 많이 구매되는 상품 데이터가 있다면 Collaborative Filtering처럼 "비슷한 가구가 많이 산 상품"도 함께 추천할 수 있으나, 해당 데이터가 없어 현실적으로 구현 불가
- **구매 이력 미반영** — 세션/계정 관리가 된다면 과거 구매 이력을 축적해 해당 가구의 실제 취향을 점진적으로 학습, 추천 정밀도를 높일 수 있음
- **AI 결과 캐싱 없음** — 동일 상품 재방문 시 API 재호출 
- **성분 정보 한계** — GPT 예측에 의존, 실제 성분표와 다를 수 있음
